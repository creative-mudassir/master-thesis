| D2 | 2026-11-03 (confirmed with data the same day) | Monthly composites for **April–October** (7 time steps) instead of 12 months | Checked for Kolomna 2021 from STAC metadata of 718 Sentinel-2 L2A scenes (`outputs/tables/kolomna_snow_by_month.csv`, `aoi_scene_counts.csv`, figure `kolomna_snow_by_month.png`). **Snow (Dec–Mar):** median snow/ice on clear scenes (cloud < 20%) is 78.8% (Dec), 79.6% (Feb), 81.0% (Mar) → the land surface is hidden even when the sky is clear. **Clouds (Nov, Jan):** January has 0 clear dates (median scene cloud 96.9%), November 3 (89.5%); November is cloudy, not snowy (0.02% snow on its 3 clear scenes). **Apr–Oct:** 44 clear dates (6.3 per month, every month ≥ 2) vs. 18 in Nov–Mar (3.6 per month); snow on clear scenes ≤ 2.7% (April) and ≤ 0.03% May–Oct. Note: Feb–Mar have as many clear dates as Apr–May, so clouds alone would not justify dropping them; snow does. Limits: snow % and cloud % are per whole MGRS tile, not only the AOI; September is weak (2 clear dates) but kept so the season is continuous |
| D3 | 2026-11-03 | Snow (SCL 11) is kept, not masked | Snow is real surface information in April/October; masking it would empty those months |
| D4 | 2026-11-03 | Months without any valid observation are gap-filled with the training mean (0 after normalisation), identically in all systems | One simple rule that every system can apply |
| D5 | 2026-11-03 | ESA WorldCover 2021 is used as the reference label; accuracy = agreement with WorldCover, not ground truth | WorldCover is itself a model product (reported global overall accuracy about 77% for v200) → threat to validity |
| D6 | 2026-11-03 | Models are trained once, on the cloud-native cube; other systems only prepare data and run inference | Fair comparison: differences come from the systems, not from retraining |
| D7 | 2026-11-03 | In lazy systems (odc-stac, ODC) W2 cube construction and W3 masking/compositing are timed as one stage | Loading and computing happen together when the lazy graph is executed |
| D8 | 2026-11-03 | Crop-type task (Task 2) is not run for the Moscow AOI | EuroCrops does not cover Russia; no open parcel-level crop labels available for the area |
| D9 | 2026-11-03 | Test metrics use only test-block pixels at least 32 px (`split.margin_px`) away from the block edge | Same buffer as the training data; a CNN would otherwise see training pixels as context at block edges |
| D10 | 2026-11-03 | A scene that cannot be read (after 10 GDAL retries) makes that month FAIL instead of being silently skipped | Silently dropped scenes would change the composite and look like a system difference; failures are logged and the month is rerun |
| D11 | 2026-11-03 | Timing analysis uses only rows with `status == ok`; memory is reported as peak RSS sampled every 0.25 s during the stage | Interrupted/failed runs are not valid timings; end-of-stage memory would underestimate the peak |
| D12 | 2026-11-03 | GPU training is not bit-for-bit repeatable; reproducibility of models is reported as the spread over 3 seeds, and the exported ONNX files (not retraining) are what all systems use | cuDNN kernels are non-deterministic; system comparison stays exact because every system runs the same ONNX file |
| D13 | 2026-11-03 | Shrub, Bare and Wetland stay in the label set (8 classes, `workflow.yaml` unchanged), but results are interpreted for the **5 main classes** (Tree, Grass, Crop, Built, Water). **Both metrics are reported** in `accuracy_<tag>.csv`: `macro_f1` (all classes present in the test pixels) and `macro_f1_main` (main classes only). Main classes are not hardcoded: `09_evaluate.py` takes every class with ≥ 1% of the labelled pixels in the AOI's 10 m labels and saves the list in the `main_classes` column. Synthetic check: `tests/test_metrics.py` | In Kolomna they are together 0.30% of pixels (WorldCover 2021, 100 m quick look, `outputs/tables/aoi_class_shares.csv`): Shrub 0%, Bare 0.17%, Wetland 0.12%. Main classes: Tree 47.5%, Crop 24.4%, Grass 23.5%, Built 2.6%, Water 1.7%. Too few samples to train or evaluate the rare classes reliably; they are also below the 0.5% threshold that `assign_blocks` uses to balance splits. To re-check with the 10 m labels (`label_shares_kolomna_50km.csv`) after Step 3 |
| D14 | 2026-11-03 | Scene pre-filter `scene_filter.max_scene_cloud_cover` raised from **60 to 80%** (`workflow.yaml`). **GEE and openEO must apply the same 80% filter on their own scene cloud metadata** (GEE `CLOUDY_PIXEL_PERCENTAGE < 80`, openEO `eo:cloud_cover < 80`); the pixel mask rule (SCL classes removed: [0, 1, 3, 8, 9, 10]) stays the same in all systems | Tested at 10 km for Apr–Oct (`scripts/03b_test_scene_filter.py`, `outputs/tables/scene_filter_test_m04-m10_kolomna_10km.csv`). **60 → 80:** scenes 39 → 48, pixels without a valid observation 1.45% → 1.00% (mean over 7 months), water pixels empty 7.96% → 3.43%, bright pixels (B02 > 2000, non-built) 0.42% → 0.31%, build time 69.1 → 71.7 s (smaller than the network run-to-run noise). The gain is mainly **September** (1 → 3 scenes; no valid obs. 8.39% → 5.27%; water empty 46.36% → 14.82%) and **April** (bright 1.58% → 0.73%); May, Jun, Aug, Oct are unchanged or differ by ≤ 0.01; no month became brighter, so the SCL mask handles the extra cloudy scenes. 100% (no filter) was tested for September only (`scene_filter_test_m09_kolomna_10km.csv`): 12 scenes, water empty 11.15%, about 10× more download for a small further gain, so not used. **SCL finding (September):** on the only clear date at 60% (2021-09-13, 11% scene cloud) the empty river pixels were mostly SCL **10 thin cirrus (35.9% of water pixels)** and partly **3 cloud shadow (10.5%)**; 44.0% were classified as water (`scene_filter_test_m09_kolomna_10km_scl_water.csv`). Whether this is real thin cloud or misclassified water is not tested; the mask is not changed for it, because a system-specific mask would break comparability. Limits: one 10 km box, one year; re-check the September water gap in the 50 km cube |
